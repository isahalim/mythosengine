## 2026-08-28 — Phase 8: Worker API/hardening/provisioning, plus a Groq tool-calling chat console

**Context and scope resolution:** the operator's request bundled several asks in one message, some in direct tension with this project's own architecture: a YouTube auto-upload button in the same breath as "no more automatic uploads"; a 3D/liquid-glass hero landing page already declined once in Phase 7 for a documented reason; and a ChatGPT-style prompting surface using Groq + "MCP" to drive the console from natural language. Resolved via `AskUserQuestion` and a written plan (approved) before any code: **manual-only YouTube upload, no button, no OAuth, ever** (unchanged from `ARCHITECTURE.md` §9's design); **the landing page stays out of scope** for this session — a real public marketing surface is genuinely separate work with no dependency on anything below, left for its own session; **this session builds Phase 8 and the chat agent together**, explicitly overriding the one-bounded-task-per-session default at the operator's request.

**What changed — Part A, Phase 8 (`AGENT_PLAYBOOK.md`, `ARCHITECTURE.md` §6/§7):**

- **Auth.** `src/server/auth/{webauthn,session,reauth,challenge-store}.ts` — full passkey register/authenticate/reauth ceremonies via `@simplewebauthn/server` (npm-viewed before adding: published 2020, active maintainer), a hand-rolled HMAC-SHA256 `__Host-session` cookie (no JWT library — the Worker's native `crypto.subtle` already does everything one would add), and step-up reauth nonces. Enrollment closes for good at 2 registered credentials, checked by row count rather than a separate counter. Pending WebAuthn challenges and reauth nonces live in new D1 tables (`webauthn_challenges`, `reauth_nonces`) and are consumed via a single atomic `UPDATE ... RETURNING`, the same pattern `db/footage-select.ts`'s `claimNextFootageSegment` already established — no read-then-write race window, and no drizzle `.transaction()` needed for a single-statement operation.
- **Vault.** `src/lib/vault.ts` — AES-GCM (96-bit random IV, AAD binds ciphertext to `name:version` so a version can't be replayed under a different key name), versioned KV keys, 24h-retained previous version. `vault.get()` (the only method that ever decrypts) has exactly one production call site, `src/lib/drivers/resolve-groq-driver.ts`, inside `src/lib/drivers/**` per `CLAUDE.md`'s NEVER block; a new ESLint rule (`no-restricted-syntax` matching `<local-var-named-vault>.get(...)` outside `src/lib/drivers/**`) enforces this by convention rather than by type — flagged as a heuristic, not an airtight guarantee, in the hardening table below. A separate `getMetadata()` reads fingerprint/last4/version without ever decrypting, for the console's key-status display.
- **Console REST API.** `src/server/router.ts` implements every route in `ARCHITECTURE.md` §6, each a thin wrapper around a service function in `src/server/console/*.ts` (`settings`, `exports`, `keys`, `dispatch`, `killswitch`, `scripts`, `summary`, `chat`) — the same functions Part B's chat agent calls, so the audit trail and "nothing hides an action from the reviewer" guarantee hold regardless of who triggered an action. Every mutating route writes to `audit_log`.
- **Real contract discovery:** Phase 7's frontend (`src/console/lib/{api,types}.ts`) already committed to a specific wire shape — `PUT /console/settings` activates a full directive directly (no draft-token handshake), `DryRunResult` is `{wouldSkip, wouldPick}` with no version field, `ExportListItem`/`ConsoleSummary` need denormalized joins (footage game, TTS voice, script hook) and several fields no runner yet populates (quota usage, live TTS/key status). The service layer was built to match that shipped contract exactly rather than inventing a cleaner one — usage-today numbers in `QuotaSnapshot` are honestly `0` (no token accounting exists yet), and key/TTS `status` is `"unknown"`/`"down"`, never a fabricated `"live"`, until a real periodic check exists.
- **`/console/settings` path collision, found and fixed:** it's both an Astro page (`src/pages/console/settings.astro`) and this API's `GET` route at the identical path. Fixed by requiring `Accept: application/json` for a `/console/*` GET to be treated as an API call (`src/console/lib/api.ts`'s `get()` now sends it); a bare browser navigation has no such header and falls through to `env.ASSETS` untouched. Covered by a router test.
- **Reused drizzle across two dialects, hit real friction:** `db/client.ts`'s `AppDb = BetterSQLite3Database | DrizzleD1Database` union (test dialect vs. production D1) breaks TypeScript's overload resolution specifically on `.returning(partialFields)` and `.transaction()` — not on plain select/insert/update chains, which work fine. Fix: `.returning()` with no field selection (then destructure in JS) instead of the partial-fields overload, and a hand-written `execAtomic()` (`db/client.ts`) using D1's native `.batch()` / better-sqlite3's native `.transaction()` for the one genuinely-two-statement-type mutation (`resetToDefaults`'s supersede-then-insert) — real atomicity without fighting drizzle's cross-dialect generics.
- **Recovery codes: PBKDF2-SHA256, not Argon2id** as `CONSOLE_SPEC.md` literally names. Argon2id has no Web Crypto implementation; every practical option needs a wasm dependency disproportionate to 8 one-time codes. Generation + hashed storage (`recovery_codes` table) is built; a redemption endpoint is out of scope — it isn't in `ARCHITECTURE.md` §6's route table.
- **Structured logging: `pino/browser.js`, not plain `pino`.** Confirmed by actually trying it: `import pino from "pino"` resolves to the Node build under `nodejs_compat` and tries to open a real file descriptor via `sonic-boom`, which `workerd` can't do. The explicit `pino/browser.js` entry point with a `write` callback never touches `fs`. A `.d.ts` shim (`src/types/pino-browser.d.ts`) re-exports the main package's existing type, since pino ships types for the default entry only.
- **Discord alerts built, not yet wired to a caller.** `src/server/alerts/{discord,rules}.ts` implement all four `AGENT_PLAYBOOK.md` Part IV conditions and are fully tested, but nothing invokes `checkAndAlert` — the WATCH→...→EXPORT runner these are meant to fire at the end of doesn't exist in this codebase (it's a GitHub Actions job, not built in this phase). Same "build the checkable unit, wire in the caller when it exists" pattern as `src/lib/drivers/embed-local-minilm.ts`'s typed stub.
- **`POST /console/dispatch` records intent, doesn't trigger anything.** No GitHub Actions `workflow_dispatch` credential is provisioned (`PROVISIONED.md` lists none) — the route inserts a real, auditable `runs` row and says so honestly in its response `note` rather than fabricating a triggered run. A killswitch-off dispatch attempt now also records a `runs` row (`status: 'skipped'`, `errorClass: 'pipeline_disabled'`) — `CONSOLE_SPEC.md` §6 acceptance test 6 requires the killswitch path to "say so in runs," which the first pass of this route missed.
- **Login/enrollment frontend, added though not originally itemized for this phase:** without it, nothing built this session is reachable — every `/console/*` page needs a session and nothing produced one. `src/pages/console/login.astro` + `src/console/scripts/login.ts` (`@simplewebauthn/browser`, npm-viewed: published 2020, same maintainer as `/server`) cover register + sign-in; a `POST /auth/passkey/logout` route and a "Sign out" button in `ConsoleShell.astro` were added alongside it. **Known limitation, not fixed here:** logout clears the browser's cookie (`Max-Age=0`) but the signed session token itself stays valid for its remaining TTL if it were ever captured before logout — there's no server-side revocation list. Session tokens are stateless by design (no D1 round-trip to check every request); adding revocation means a real session store, which is more than this pass's scope.
- **Provisioning (Task 8.2) — real infrastructure, done in this session:** D1 database `mythosengine` (`77a0969e-2fb8-460e-9e52-f2606b2fa2fa`, region WNAM) and KV namespaces `HOT` (`e1a2adff832742ae8953cab9905a7aa6`) / `VAULT` (`84b02470f3ca4e65807ba09c53cbe426`) created via the `cloudflare-bindings` MCP tools, after confirming both were empty. All 7 committed migrations applied via `wrangler d1 execute --remote`; `wrangler.toml` updated with the real bindings; `worker-configuration.d.ts` regenerated. `/readyz` now actually probes `env.DB`/`env.HOT` instead of a hardcoded 503. `PROVISIONED.md` updated with the real IDs so no future session tries to recreate them. Not deployed — `wrangler deploy` is a separate, explicitly-confirmed action per this session's own executing-actions-with-care discipline, and the existing GitHub Actions CD deploys on push to `main` anyway.

**What changed — Part B, the Groq tool-calling chat console:**

- **No literal runtime MCP server**, despite the operator's wording. This repo already resolved the identical question for `edge-tts-mcp` (2026-08-27 entry below): MCP is right for a *development-time* agent exploring a tool, not for a *production* Worker request talking to its own code — there's no persistent process for an MCP server to live in inside a Workers request, and Groq's Chat Completions API already speaks the same "tool schemas in, tool_calls out" shape MCP itself is built on. The chat agent uses Groq's native OpenAI-compatible tool calling instead: `src/lib/drivers/types.ts`'s `LlmRequest`/`LlmResponse` gained optional `tools`/`toolChoice`/`toolCalls` (additive; every existing caller of `GroqLlmDriver` is unaffected), `groq.ts` marshals both directions including the null-content-on-a-tool-call-turn case.
- **`src/server/agent/tools.ts` — 8 tools, all delegating to the exact service functions the REST routes call:** `get_summary`, `list_exports`, `get_export`, `mark_export_reviewed`, `discard_export`, `get_settings`, `propose_settings_update` (preview only, mirrors the frontend's own dry-run-then-activate flow), `activate_settings_update`, `dispatch_run`. **Key rotation and the killswitch have no tool, on purpose, not by oversight** — both require a fresh WebAuthn assertion an LLM cannot produce, and both are exactly the two actions whose blast radius (credential swap, halting the pipeline) shouldn't be reachable from a natural-language inference. Every tool call, successful or not, writes to `audit_log` with `actor: 'agent'`.
- **`src/server/agent/loop.ts`** runs the tool-calling loop (bounded to 6 iterations, guaranteed termination), persisting every step to the new `chat_sessions`/`chat_messages` tables — a `'tool'`-role row carries the tool name, its arguments, and its result, and doubles as the source for reconstructing the OpenAI-wire `assistant`-with-`tool_calls` + `tool`-result message pair on the next turn (the row's own id becomes the wire `tool_call_id`), so no separate "assistant announced a tool call" row is needed.
- **Frontend:** `src/pages/console/chat.astro` + `src/console/scripts/chat.ts` — session sidebar (ChatGPT pattern, title derived from the first message), message thread, composer. Tool calls render as a distinct `→ ran <tool>` line so the operator always sees what actually happened, not just prose, matching `CONSOLE_SPEC.md`'s "nothing hides an action from the reviewer" guarantee applied to the agent too. No streaming (SSE) — single JSON response per turn, a deliberate scope cut to keep the Workers request model simple; addable later without changing the tool contract.
- Total console bundle after all of Part A + B (WebAuthn browser lib, chat UI, login UI): **30 KB gzipped**, against the 200 KB budget.

**Design-direction conflict, resolved with the operator before writing code:** the operator's request referenced 21st.dev hero landing pages, interactive 3D, liquid glass, and rainbow gradients. `AGENT_PLAYBOOK.md` Phase 7 and `ARCHITECTURE.md` §8 both explicitly rule out a public marketing hero for the console ("skip straight to the dashboard"), and `CONSOLE_SPEC.md` sets a ≤200KB gzip console bundle budget and a "zero console errors + clean a11y pass" bar, not a Lighthouse/visual-spectacle one. No WebGL, no 3D, no new UI framework, no public-page changes.

**Discovered mid-build: `output: "static"` (astro.config.mjs) means every console page is prerendered at build time with no per-request data — Astro components can't render variable-length runtime lists at all.** The original plan called for Astro components (`KeyRow`, `ReviewQueueRow`, `AuditFlagList`, `SettingsSummary`, `LiveStatusDot`) mirroring `CONSOLE_SPEC.md`'s UI descriptions. Once actually wiring data through, it became clear these would only ever render placeholder/empty markup — the operator's real exports, keys, and audit flags don't exist until a runtime fetch to `/console/*` resolves, long after the static HTML has already shipped. Deleted those five files rather than keep them as inert scaffolding; the equivalent rendering now lives in `src/console/scripts/{dashboard,keys,review-queue}.ts` as plain `document.createElement`/`textContent` DOM construction (never `innerHTML` — summary fields ultimately trace back to LLM output and third-party feed text, which `CLAUDE.md`'s NEVER block treats as data, not something to trust). `BentoCard.astro`, `ConsoleShell.astro`, and `QuotaMeter.astro` survive because they render a fixed, known structure (card chrome; four named quota meters) that JS only ever updates in place by id, never regenerates. Switching to Astro SSR (a `@astrojs/cloudflare` adapter) would avoid this split but is a real architecture change outside Phase 7's scope — not attempted.

**Discovered mid-build: Cloudflare's generated `worker-configuration.d.ts` globally collides with the DOM's `Element` interface.** `wrangler types` (run via the existing `postinstall` hook) emits an ambient `interface Element { append(content: string | ReadableStream | Response, options?): Element; ... }` for the Workers `HTMLRewriter` API. Because `tsconfig.json`'s `types` array pulls that file in project-wide and TypeScript merges same-named global interfaces, every DOM `Element`-derived type's `.append()` (and `.before()`/`.after()`/`.prepend()`/`.replace()`) got a second, incompatible overload — `form.append(input, rotateButton, testButton)` failed to typecheck with "Expected 1–2 arguments, but got 3" and an unrelated-looking "HTMLFormElement is missing properties from Response." This is the first client-side DOM code in the repo, so nothing had tripped over it before. **Fix:** use `appendChild` (one node at a time) instead of the variadic `.append()` in browser-facing console code — `appendChild` isn't part of Cloudflare's merged surface. `replaceChildren()` (used elsewhere in the same files) is unaffected and was left as-is. Considered splitting into a separate `tsconfig` for browser-only code (the more structurally correct fix, since this landmine now applies to *any* future DOM code anywhere in the project) but that's a repo-wide TypeScript project-structure change, out of proportion to Phase 7 alone — left as a known constraint, documented here and inline in `keys.ts`, not fixed at the root.

**`dependency-cruiser` (named in `CONSOLE_SPEC.md` §5 for the console/public bundle-isolation rule) was not added.** Its `.astro`-file import-parsing support wasn't verified in this session, and a tool that silently doesn't check `.astro` frontmatter imports would be worse than no tool — false confidence instead of an honest gap. Wired into `pnpm verify`. Revisit `dependency-cruiser` if the check ever needs to catch more than direct import statements (e.g. dynamic imports, re-exports).

**`dispatchRun` (POST `/console/dispatch`, "trigger a pipeline run ad hoc," `ARCHITECTURE.md` §6) got a "Run now" button on the Pipeline pulse card** — not originally itemized in `CONSOLE_SPEC.md` §4's card table, but the route is real and documented, and `knip` correctly flagged the client function as unused dead code once written without a caller. ## 2026-08-27 (very late, post-pivot, fix) — `verify` CI failure: `worker-configuration.d.ts` isn't in git, and never got regenerated in CI

**What broke:** the first push to `main` after the CD change (`1b4e017`) failed `CI / verify (push)` with `TS2688: Cannot find type definition file for './worker-configuration.d.ts'`. Separately, the same push showed a *second*, independent failure: Cloudflare's own native "Workers Builds" git integration (a pre-existing auto-deploy path this repo's docs never recorded — see the entry directly below) failed at `pnpm install --frozen-lockfile` with `ERROR packages field missing or empty`.

**Why `worker-configuration.d.ts` broke:** `tsconfig.json`'s `compilerOptions.types` points at `./worker-configuration.d.ts`, but `.gitignore` deliberately excludes that file — it's a `wrangler types` codegen artifact (583KB, regenerated from `wrangler.toml`'s bindings), the same category as a `.d.ts` equivalent of a lockfile. It existed on the operator's machine because an earlier session ran `wrangler types` locally, but was never committed, so every fresh checkout (every CI run, ever) was missing it. This was latent from the moment `types: ["./worker-configuration.d.ts"]` was added to `tsconfig.json` — `pnpm verify` only ever ran locally where the file happened to already exist, and `CI / verify` had apparently never been checked before (deploys were manual, so nobody had a reason to look at the Actions tab).

**Fix:** added `"postinstall": "wrangler types"` to `package.json`. `wrangler types` needs no network access or credentials — it derives entirely from `wrangler.toml` — confirmed by deleting the file and regenerating it offline before committing to this fix. Verified against a true fresh install (`rm -rf node_modules worker-configuration.d.ts && pnpm install --frozen-lockfile`, matching what CI actually does) that the file is regenerated automatically, then reran the full `pnpm verify` gate clean. This fires identically for every `pnpm install` — local, `CI / verify`, and `CI / deploy` — so there's exactly one place this is defined, not a CI-only special case.

**What was explored and rejected for the Cloudflare "Workers Builds" failure — do not repeat this path without rereading this entry:** the `pnpm install` error there is a real, pnpm-documented bug (`pnpm/pnpm#9361`, `#8968`): a `pnpm-workspace.yaml` with only `overrides`/`allowBuilds`/`minimumReleaseAgeExclude` keys and no `packages:` field throws "packages field missing or empty" on pnpm versions before 10.5. The documented fix is adding `packages: ["."]`. That fix was implemented, tested, and works — but adding `packages:` to `pnpm-workspace.yaml` causes `semgrep`'s `package_managers.pnpm.*` ruleset to start analyzing the file for the first time (confirmed: 0 findings on the original file, 3 blocking findings the moment `packages:` is added) and it demands `blockExoticSubdeps: true`, `trustPolicy: no-downgrade`, and a real `minimumReleaseAge` (not `0` — semgrep treats `0` as "unset," confirmed by testing). The first two are free wins (no exotic/git-URL deps in this lockfile, applied with zero risk). `minimumReleaseAge: 10080` (the value `minimumReleaseAgeExclude`'s pre-existing 4-package list was clearly prepared for, but apparently never actually wired in) is not free: it rejects the *current, working* lockfile outright — 71 entries, mostly `workerd`/`sharp` platform binaries that publish near-daily — even under `pnpm install` (non-frozen); pnpm refuses to even attempt re-resolution and requires `pnpm clean --lockfile` (a full fresh re-resolution of all 627 entries) before the policy can be satisfied. That is a materially different, riskier change — every transitive dependency across the project potentially moves, needing a full re-verify to rule out regressions — not something to fold into a "fix the failing build" task without the operator's sign-off. **Not done this session.** `pnpm-workspace.yaml` was reverted to its original, unmodified state; the Cloudflare-side install error is still present.

## 2026-08-27 (later night) — tts-edge.ts: subprocess to a Python wrapper, not a hand-rolled protocol or an npm import

**What changed:** implemented `src/lib/drivers/tts-edge.ts` + `scripts/edge_tts_synth.py`. The driver shells out to the wrapper script (`node:child_process.execFile`), which imports the `edge_tts` Python library (LGPL-3.0, `rany2/edge-tts`) directly and requests `WordBoundary` events explicitly. Real end-to-end smoke test passed: real audio bytes + real word-level timings (`startMs`/`endMs` per word) from the live, unauthenticated Microsoft endpoint. 6 contract tests against fixture Python scripts (success, malformed JSON, missing output files, non-zero exit/retry, hang/timeout, missing interpreter).

**Why, and what was rejected — this took three iterations before landing on the actual implementation:**

1. **Rejected: hand-rolling the WebSocket protocol in TypeScript**, as `ARCHITECTURE.md` originally implied ("speaks the underlying protocol directly"). Research turned up that Microsoft rotates a `Sec-MS-GEC` auth token derived from the Chromium version on every Edge release, and the reference Python project runs a *daily CI job* just to detect when it's gone stale. Reimplementing that from scratch in one session, with no ongoing maintenance capacity, would have shipped a driver that quietly breaks the first time Microsoft ships a new Edge build.
2. **Rejected: importing a JS port as an npm dependency** (`edge-tts-universal`, `@andresaya/edge-tts`, `@travisvn/edge-tts`) — checked their licenses before adding any of them (same `npm view`-style diligence as every other dependency) and found every JS port of this library is AGPL-3.0 or GPL-3.0. That's a real, consequential licensing decision — copyleft obligations, especially AGPL's network-use clause, aren't something to pull into a dependency tree silently on the operator's behalf.
3. **What was actually built:** the original Python `edge_tts` library is LGPL-3.0 — meaningfully weaker copyleft, and more to the point, invoking it as a **separate OS process** (not a code import) sidesteps the linking question for the TypeScript codebase entirely, under any reading of any of these licenses. This is exactly the same pattern already established for `yt-dlp` and `ffmpeg` — Python/native CLI tools invoked via `child_process`, never imported. `scripts/edge_tts_synth.py` exists specifically because the bare `edge-tts` CLI hard-codes sentence-level subtitle boundaries with no flag to select word-level (confirmed by actually running it and reading the library source — the CLI's SentenceBoundary default surprised me, ARCHITECTURE.md originally assumed word-level was the default output). The 30-line wrapper script calls the library's `Communicate` class directly with `boundary="WordBoundary"` instead.

`ARCHITECTURE.md` §0/§5.6, `CLAUDE.md`'s stack list, and `AGENT_PLAYBOOK.md`'s Phase 1 task were all updated to describe what was actually built, not the original guess.

## 2026-08-27 (evening) — Project pivot: MythosEngine → AutoShorts AI

**What changed:** the entire product direction. `CLAUDE.md`, `PROVISIONED.md`, `ARCHITECTURE.md`, `AGENT_PLAYBOOK.md`, and `CONSOLE_SPEC.md` were rewritten from a game-news publishing site to an autonomous YouTube Shorts pipeline (trend ingestion → scripted narration → gameplay footage → TTS + captions → FFmpeg render → policy gate → YouTube upload), at the operator's explicit direction. Same repo, same Cloudflare Worker (`mythosengine` — kept as the technical name; the product is branded AutoShorts AI in the console only), same driver-abstraction philosophy, same verify gate. `.mcp.json` gained an `edge-tts-mcp` entry (`uvx edge_tts_mcp`, verified against PyPI, not guessed).

**Why:** operator's explicit request to redirect the project. Three consequential decisions were resolved via clarifying questions before writing anything, because they're genuinely hard to reverse once code depends on them:

1. **Footage sourcing.** Literally "download trending game gameplay" means scraping other creators' videos — real copyright exposure regardless of transformation. Operator's resolution: source from long-form walkthrough/guide creators specifically (their content functions more like movies/guides, arguably strengthening a transformative-use position), scraped **weekly** (not per-render) to find each tracked channel's current most-watched video, clip different random high-action segments from the same source video across many renders. This is now `footage_sources`/`footage_segments` + the weekly FOOTAGE REFRESH stage (`ARCHITECTURE.md` §5.0). **Stated plainly, not downplayed:** downloading the source video via `yt-dlp` is itself a YouTube ToS matter, separate from whether the resulting heavily-cropped, narrated, captioned clip is transformative enough to be defensible. Isolating this to one weekly, low-volume, fully-audited job (never inline in the daily render) is the mitigation chosen here — not a claim of zero risk. If a strike or takedown ever happens, start the postmortem at this stage.
2. **TTS provider.** Operator chose Microsoft Edge's unofficial "Read Aloud" TTS (the same protocol the `edge-tts` library and `edge-tts-mcp` wrap) over Inworld, specifically for its $0 permanent cost. Traded off against MythosEngine's old "prime directive: permanent free tier" — this qualifies, but it's an unofficial API with no SLA, not a contractual free tier. The driver-abstraction pattern exists precisely so a paid fallback is one new file + one env var if Microsoft ever closes it off; `ARCHITECTURE.md` §0/§9 calls this out as a reliability risk to alert on, not a cost risk to budget for.
3. **YouTube policy-suspension risk.** Current (2025-renamed) "inauthentic content" policy explicitly three-strikes mass-produced/templated/reused-visual channels — close to a literal description of the naive version of this pipeline. Operator chose to bake in an explicit POLICY GATE (`ARCHITECTURE.md` §9): an originality-score floor from an adversarial critic pass, footage rotation tracking so the same clip doesn't repeat, script-similarity checks against upload history, and the synthetic-media disclosure flag on every upload. Mirrors MythosEngine's citation-verification gate — same "the model never publishes/uploads, a deterministic check decides" philosophy, redirected at a different risk.

MCP clarification worth recording since it's a recurring source of confusion: "MCP-compatible TTS" was interpreted as *"give the coding agent a way to test TTS during development,"* not *"the deployed pipeline calls an MCP server at runtime."* The latter isn't how MCP is meant to be used — it's an agent-tool protocol, not a backend integration pattern. `src/lib/drivers/tts-edge.ts` (Phase 1, not yet written) will speak the underlying protocol directly, matching every other driver's shape.

**What was rejected:**
- **Inworld TTS** — confirmed via research to have no recurring free tier (one-time ~40-70 min trial, then $15-35/million characters, roughly $2-5/month at this project's volume). Not expensive, but it broke the "permanent, card-free" test Edge TTS passes. Kept as the obvious first fallback if Edge TTS ever dies — the interface (`TtsDriver`) doesn't care which one is behind it.
- **A live per-run scraper with no maintained library** — the operator's actual answer (weekly refresh into a library) already avoids this; recorded here because it was the more dangerous alternative that was explicitly steered away from during the design conversation.
- **Cloudflare R2 for the footage library** — still requires a card to activate even on the free tier (same finding as MythosEngine's original v1.0→v1.1 revision). A git orphan branch holding only short, already-transformed clips (not full source videos) fits the "small rotating library" use case without reopening that constraint.
- Renaming the Worker/repo to match the new product name — infra churn for a cosmetic change; the product is branded AutoShorts AI in the console UI, the technical substrate keeps its existing name.
